## Explain the concept of hoisting in relation to `var`.

### The Concept of the Execution Context

To understand hoisting, one must first look at how the **JavaScript Engine** (like V8) processes code. When your script runs, the engine creates an **Execution Context**. This process happens in two distinct phases: the **Creation Phase** and the **Execution Phase**. During the Creation Phase, the engine scans the code for variable and function declarations before a single line of code is actually executed. It sets aside memory space for these declarations in a process conceptually described as "lifting" or "hoisting" them to the top of their containing scope (global or function).

### Hoisting with `var`

When a variable is declared using the `var` keyword, the JavaScript engine allocates memory for it during the Creation Phase and initializes it with the default value of **`undefined`**. This is a critical distinction from `let` and `const`, which are also hoisted but remain uninitialized (leading to the Temporal Dead Zone).

Because the memory is allocated and a value (`undefined`) is assigned before the code runs, you can reference a `var` variable in your code *before* the line where it is formally declared without triggering a ReferenceError.

* **Declaration vs. Initialization**: Only the **declaration** is hoisted, not the **assignment**. If you write `var x = 5;`, the engine treats it as two steps: `var x;` (hoisted to the top) and `x = 5;` (stays in place).

* **Functional Scope**: `var` is function-scoped. If hoisted inside a function, it moves to the top of that function. If declared outside, it moves to the top of the global scope and becomes a property of the global object (e.g., `window` in browsers).

* **Re-declaration**: `var` allows for multiple declarations of the same variable name within the same scope. The engine simply ignores subsequent `var` keywords and treats them as re-assignments.

### Technical Example and Engine Behavior

Consider the following snippet:

```javascript
console.log(nickname); // Output: undefined
var nickname = "Gemini";
console.log(nickname); // Output: "Gemini"

```

**What the Engine Sees (Conceptual "Hoisted" Version):**

```javascript
var nickname;          // Memory allocated, initialized to undefined
console.log(nickname); // Accesses the initialized value
nickname = "Gemini";   // Assignment happens here
console.log(nickname); // Accesses the updated value

```

In the first line, the engine does not crash because `nickname` exists in the **Variable Environment** of the execution context. However, because the assignment `"Gemini"` hasn't happened yet, it returns the default `undefined`.

### Historical Context and "Quirks"

Hoisting was originally designed to allow **Function Declarations** to be used before they were defined, which enabled more flexible code organization (placing "main" logic at the top and helper functions at the bottom). Variable hoisting with `var` was a side effect of this implementation.

This behavior is often cited as a source of bugs, especially in loops:

* **The Loop Problem**: Because `var` is not block-scoped, a variable declared inside a `for` loop is hoisted to the top of the function. This means all iterations of the loop share the *same* variable instance in memory. This led to the famous "closure in a loop" bug before `let` provided block-scoping.
